## 1. Что такое Brain

**OSA Brain** — интеллектуальное ядро AI Business OS.

Это не интерфейс, не база данных и не отдельная модель. Brain — **слой принятия решений**, который связывает намерение пользователя, контекст бизнеса, план работы, команду исполнителей и долговременную память в один непрерывный цикл.

Brain отвечает на вопросы:

- Что пользователь на самом деле хочет получить?
- Что уже известно о его бизнесе и прошлой работе?
- Какой план и какая команда нужны для результата?
- Когда вызывать внешний интеллект (LLM), а когда достаточно детерминированной логики?
- Что сохранить после завершения, чтобы завтра не начинать с нуля?

Brain **не говорит с пользователем напрямую** как чат-бот. Brain питает продукт: экраны, результаты, рекомендации, продолжение работы. Пользователь видит **исход**, не механизм.

```text
Пользователь (намерение, текст, выбор)
        ↓
   OSA Brain (7 уровней мышления)
        ↓
   Runtime (контекст, промпт, инструменты, события)
        ↓
   Universal AI Gateway (исполнение LLM — opaque)
        ↓
   Результат + память + следующий шаг
```

## 2. Почему это не чат

Чат оптимизирован под **обмен репликами**. OSA оптимизирована под **продвижение работы**.

| Чат | OSA Brain |
| --- | --------- |
| Сессия = поток сообщений | Сессия = задача с результатом |
| Контекст в голове пользователя | Контекст в памяти системы |
| Каждый вопрос — с чистого листа | Намерение наследует прошлые результаты |
| Пользователь выбирает модель | Brain выбирает среду исполнения |
| Успех = ответ получен | Успех = решение принято, черновик сохранён, путь продолжен |

Brain может **использовать** диалоговые модели внутри Gateway, но архитектура Brain — это **конвейер решений**, а не бесконечная лента prompt/response.

Признаки чат-архитектуры в продукте — сигнал к переработке. См. [FIRST_FEELING.md](../brand/FIRST_FEELING.md).

## 3. Семь уровней мышления

Brain работает как стек из семи уровней. Нижние уровни могут выполняться без LLM; верхние уровни координируют нижние. Не каждая задача проходит все семь уровней с одинаковой глубиной — Brain **масштабирует глубину** под сложность намерения.

### 3.1 Intent (Намерение)

**Вопрос уровня:** *Что пользователь хочет получить, а не что он буквально написал?*

- Приём цели, формулировки, выбора из быстрых шаблонов
- Нормализация языка: бизнес-результат, не технический запрос
- Привязка к категории работы (стратегия, контент, поиск клиентов, анализ…)
- Решение: нужно ли уточнение до старта (один раунд, не бесконечный опрос)

Intent — **входной контракт** Brain. Без связанного намерения Gateway не вызывается ради «красивого ответа».

### 3.2 Diagnosis (Диагностика)

**Вопрос уровня:** *В какой ситуации находится пользователь и что мешает результату?*

- Оценка полноты контекста: первый визит vs возвращение
- Сигналы: есть ли проект, прошлый результат, незавершённая работа
- Выявление пробелов: не хватает цели, срока, аудитории, ограничений
- Уровень уверенности: можно ли действовать сразу или нужна одна точечная уточняющая ветка

Diagnosis — преимущественно **детерминированный** слой. LLM не должен «угадывать», что спросить, если правила продукта уже знают ответ.

### 3.3 Mapping (Картирование)

**Вопрос уровня:** *Как эта задача ложится на карту бизнеса пользователя?*

- Связь намерения с проектом, направлением, прошлым результатом
- Подбор релевантных знаний (документы, факты, CRM-сигналы — когда подключены)
- Определение границ задачи: что входит в первый черновик, что отложено
- Формирование **контекстного пакета** для следующих уровней

Mapping превращает абстрактное «хочу» в **адресуемую работу** внутри операционной системы бизнеса.

### 3.4 Planning (Планирование)

**Вопрос уровня:** *Какие шаги ведут к результату?*

- Декомпозиция на этапы: понять → собрать → оформить → проверить
- Выбор глубины: один проход vs многошаговая координация
- Определение артефакта: план, текст, список, структура, рекомендация
- Оценка длительности и ожиданий для пользовательского copy (без технических таймеров)

Planning задаёт **форму результата**, который пользователь увидит на экране. См. [REASONING_ARCHITECTURE.md](./REASONING_ARCHITECTURE.md).

### 3.5 Memory (Память)

**Вопрос уровня:** *Что мы уже знаем и что должно пережить эту сессию?*

- Чтение: факты о бизнесе, итоги прошлых run, привязка к проекту
- Запись: что сохранить после успеха (не сырой лог чата)
- Политика забывания: что ephemeral, что долгоживущее
- Персонализация возврата: «вчера мы…», «продолжить с…»

Memory — **моат продукта**. Brain без памяти превращается в чат.

### 3.6 AI Team (Команда)

**Вопрос уровня:** *Кто выполняет части работы и в каком порядке?*

- Подбор специализаций под задачу (стратег, исследователь, автор, аналитик — как роли, не как персонажи в UI)
- Координация: последовательно, параллельно, с синтезом
- Делегирование вызовов Gateway с разными routing-hints (категория, сложность, длина контекста)
- Сборка единого результата из частей — пользователь видит **один** deliverable

AI Team — **оркестрация**, не «чат с десятью ботами». Имена агентов, confidence scores и графы не показываются пользователю.

### 3.7 Navigation (Навигация)

**Вопрос уровня:** *Куда направить пользователя после и между шагами?*

- Следующий экран: продолжить, сохранить, уточнить, начать новую задачу
- Привязка результата к проекту и истории
- Рекомендация на завтра: один главный вектор, не меню из пятнадцати кнопок
- Соблюдение **одного главного действия** на экран

Navigation замыкает цикл Brain и готовит Intent следующей сессии.

## 4. Как проходит одна задача пользователя

Типовой путь — от формулировки до результата:

```text
1. INTENT
   Пользователь описывает задачу или выбирает шаблон.
   Brain фиксирует цель и категорию.

2. DIAGNOSIS
   Brain проверяет полноту контекста и уверенность.
   При необходимости — один уточняющий вопрос.

3. MAPPING
   Задача связывается с проектом, памятью, знаниями.
   Формируется контекстный пакет.

4. PLANNING
   Brain определяет план и форму артефакта.
   Пользователь видит спокойный прогресс, не внутренние этапы.

5. AI TEAM (+ Gateway)
   Координатор запускает нужные роли.
   Каждый LLM-вызов идёт через Universal AI Gateway с routing hints.
   Инструменты выполняются через Tool Executor (побочные эффекты с аудитом).

6. SYNTHESIS & QUALITY
   Части собираются в один результат.
   Проверка: отвечает ли артефакт намерению, а не только промпту.

7. MEMORY
   Сохраняются факты, привязки, итог run — по политике записи.

8. NAVIGATION
   Пользователь получает результат и один главный следующий шаг.
   Регистрация / сохранение — когда нужно закрепить работу.
```

Пользователь на всём пути видит **тишину, прогресс, результат** — не семь уровней по именам.

## 5. Как Brain взаимодействует с Universal AI Gateway

**Разделение ответственности:**

| OSA Brain | Universal AI Gateway |
| --------- | -------------------- |
| Что делать и зачем | Как исполнить вызов LLM |
| Намерение, план, команда | Маршрутизация, политика org, fallback |
| Когда вызывать LLM | Provider adapter, retry, метрики |
| Что передать в контексте | Выбор модели и провайдера (opaque) |
| Синтез и память | Токены, latency, cost (internal only) |

Brain **никогда** не выбирает провайдера напрямую и **никогда** не передаёт выбор модели в UI.

Поток вызова:

```text
Brain (Planning / AI Team)
  → формирует семантику задачи: категория, сложность, длина контекста, tools
  → Runtime собирает PromptRequest из Context + Memory + Knowledge
  → GatewayRequest с providerCode: auto и routing hints
  → Universal AI Gateway: Task Router → Policy Filter → Execution
  → GatewayResponse (content, usage — internal)
  → Brain синтезирует пользовательский результат
```

Gateway — **мускулы**. Brain — **намерение и суждение**.

Подробности Gateway: [UNIVERSAL_AI_GATEWAY.md](./UNIVERSAL_AI_GATEWAY.md).

## 6. Почему пользователь никогда не видит модели

Три причины — продуктовая, архитектурная и доверительная.

**Продуктовая.** Пользователь покупает не токены, а порядок и результат. Выбор «GPT vs Claude» — перекладывание инженерной нагрузки на человека, который пришёл за бизнес-решением.

**Архитектурная.** Brain и Gateway разделены. Маршрутизация, fallback, org policy и обучение на метриках — зона Gateway. Brain передаёт **категорию работы**, не имя вендора. UI не имеет поля для providerCode.

**Доверительная.** Показ модели создаёт ощущение «дешёвого AI» и ломает [FIRST_FEELING.md](../brand/FIRST_FEELING.md): спокойствие, уверенность, отличие от ChatGPT.

Что видит пользователь вместо модели:

- «Готовим результат…»
- «Работаем над запросом…»
- Конкретный черновик или план

Ошибки — человеческий текст без имён провайдеров.

## 7. Как Brain принимает решения

Brain использует **гибрид детерминизма и LLM**:

| Тип решения | Механизм | Примеры |
| ----------- | -------- | ------- |
| **Жёсткие правила** | Детерминированная логика | Политики памяти, org model policy, один уточняющий вопрос, запрет утечки в UI |
| **Классификация** | Правила + эвристики | Категория задачи, routing profile, длина контекста |
| **Приоритизация** | Скоринг без LLM | Порядок маршрутов Gateway, rolling stats по категориям |
| **Генерация и синтез** | LLM через Gateway | Черновик плана, текст, анализ |
| **Обучение** | Агрегированные метрики | Улучшение приоритета маршрутов по success rate — не RLHF в продукте |

**Принцип:** если решение можно объяснить таблицей правил — не отдавать его LLM. LLM — для языка, структуры и нюанса, не для маршрутизации инфраструктуры.

**Конфликты:** продуктовый канон (Product Bible, First Feeling) > Brain rules > эвристики Gateway > ответ модели.

## 8. Какие данные Brain запоминает

Brain и Memory Manager хранят **бизнес-контекст**, не переписку ради переписки.

| Категория | Примеры |
| --------- | ------- |
| **Намерения и цели** | Выбранная цель, формулировка задачи, категория |
| **Результаты** | Артефакты run: планы, черновики, структурированные выводы |
| **Привязки** | Проект, организация, пользователь, run id, correlation |
| **Факты о бизнесе** | Устойчивые сведения, явно выведенные или подтверждённые |
| **Паттерны работы** | Что пользователь продолжает, что бросает (агрегированно) |
| **Рекомендации** | Следующий шаг, «продолжить с…» для Navigation |
| **События** | Timeline run для восстановления и аудита (внутренний слой) |

Память **персонализирует** Diagnosis и Navigation при возврате.

---

## 9. Какие данные Brain никогда не хранит

| Исключено | Почему |
| --------- | ------ |
| **Сырые логи провайдеров с именами моделей в user-facing слое** | Нарушает opaque execution |
| **Полный сырой чат «как в мессенджере»** | Чат-архитектура; храним результат и факты |
| **Credentials, API keys** | Зона Gateway / tenant secrets |
| **Данные других организаций** | Tenant isolation |
| **Персональные данные без цели** | Минимизация; только для работы пользователя |
| **Промпты вендоров и system leakage** | Безопасность и переносимость |
| **Несанкционированные побочные эффекты** | Только через Tool Executor с аудитом |

Забывание — такая же политика, как запоминание. Ephemeral состояние (превью до регистрации) живёт ограниченно и не подменяет долговременную память.

## 10. Как Brain становится умнее со временем

«Умнее» в OSA — не «модель стала GPT-5». Это **компаунд контекста и качества решений**:

**1. Накопление памяти**  
Каждый завершённый результат обогащает Mapping и Navigation. Пользователь объясняет бизнес реже.

**2. Маршрутизация Gateway (детерминированная)**  
Rolling statistics по категориям задач улучшают приоритет провайдеров без участия пользователя и без AI-for-routing.

**3. Качество планов и команд**  
Эвристики team selection и planning уточняются по продуктовым метрикам (завершение, возврат, WABO).

**4. Обратная связь без опросников**  
Поведение: сохранил, продолжил, бросил, вернулся через неделю — сигналы для Brain, не обязательно явный рейтинг «👍».

**5. Знания организации**  
Подключённые knowledge sources расширяют Mapping — Brain опирается на документы бизнеса, не только на общие priors модели.

**Чего Brain не делает:** не обучает публичную модель на данных клиента; не меняет поведение хаотично между сессиями; не «умнеет» за счёт показа более сложного UI.

## Сводная схема

```text
                    ┌─────────────────────────────────┐
                    │         OSA BRAIN               │
                    │  Intent → Diagnosis → Mapping   │
                    │  → Planning → Memory            │
                    │  → AI Team → Navigation         │
                    └───────────────┬─────────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
        Context Builder      Memory Manager         Orchestrator
              │                     │                     │
              └─────────────────────┼─────────────────────┘
                                    ▼
                          Universal AI Gateway
                          (auto, opaque, policy)
                                    ▼
                              Результат
                                    ▼
                    Память + Navigation → следующий Intent
```
